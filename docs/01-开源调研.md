> 调研日期：2026-09-26　调研范围：GitHub 公开仓库

> 本文只记录**看到了什么**（含事实出处）。"看光光该怎么用"见 `02-架构方案.md`。

## 2. 前端：可借鉴的工程结构

### 2.1 `obytes/react-native-template-obytes` — 4,345★（首选参考）

Expo + TypeScript 生产级模板，结构与依赖都是当前最主流的组合。

**目录分层（`src/` 下四层）：**

```
src/
├── app/              路由层（expo-router 文件路由）
│   ├── _layout.tsx   根布局
│   ├── login.tsx
│   ├── onboarding.tsx
│   └── (app)/        路由分组：登录后的主区域
│       ├── _layout.tsx
│       ├── index.tsx
│       ├── settings.tsx
│       └── style.tsx
├── features/         业务域层：auth / feed / onboarding / settings
├── lib/              基础设施层
│   ├── api/          请求层封装
│   ├── auth/
│   ├── hooks/        通用 hooks
│   ├── i18n/
│   ├── storage.tsx   本地存储
│   └── utils.ts
├── components/       通用 UI 组件
└── translations/     文案资源
```

**关键发现：请求层只有 7 行。** 文件 `src/lib/api/client.tsx` 原文：

```ts
import axios from 'axios';
import Env from 'env';

export const client = axios.create({
  baseURL: Env.EXPO_PUBLIC_API_URL,
});
```

这推翻了一个常见做法——**不需要自己写又大又全的 request 封装**。一个 axios 实例 + 环境变量 baseURL 就够了，重试、缓存、loading、错误态全部交给 react-query。

**依赖清单（`package.json` 原文摘录，用于选型对照）：**

| 类别 | 选型 | 用途 |
|---|---|---|
| 路由 | `expo-router` | 文件路由，`main` 字段指向 `expo-router/entry` |
| 服务端数据 | `@tanstack/react-query` + `react-query-kit` | 请求缓存/重试/失效 |
| HTTP | `axios` | 传输层 |
| 表单与校验 | `@tanstack/react-form` + `zod` | 输入校验 |
| 客户端状态 | `zustand` | 少量全局状态 |
| 本地存储 | `react-native-mmkv` | 同步 KV，比 AsyncStorage 快 |
| 错误兜底 | `react-error-boundary` | 页面级错误边界 |
| 图片 | `expo-image` | 图片加载与缓存 |
| 国际化 | `i18next` + `react-i18next` | 多语言（按需） |
| 样式 | `tailwind-variants` + `uniwind` | 原子化样式 |

**环境变量与构建脚本（值得直接抄的部分）：**

```
EXPO_PUBLIC_APP_ENV=preview|development|production   # 环境开关
STRICT_ENV_VALIDATION=1                              # 环境变量缺失即报错
eas build --profile development|preview|production   # EAS 三档构建
check-all = lint && type-check && lint:translations && test   # 质量门
```

要点：**环境变量分层 + 构建分档 + 质量门脚本化**。这三件事在项目早期做，成本几乎为零；等到上线前再补，改造成本很高。

### 2.2 `thecodingmachine/react-native-boilerplate` — 5,567★

更传统的分层，路径为 `template/src/`：

```
template/src/
├── App.tsx
├── components/     通用组件
├── hooks/
├── navigation/     导航配置（非文件路由）
├── screens/        页面
├── services/       接口服务
├── theme/          主题
├── translations/
└── tests/
```

与 obytes 相比更扁平、更好懂，但缺少"业务域"概念，页面一多容易堆成杂货铺。

### 2.3 其他命中

| 仓库 | ★ | 说明 |
|---|---|---|
| `infinitered/ignite` | 19,943 | 最老牌 RN boilerplate，9 年迭代；用 MST + 自定义 CLI，**偏重**，不适合小项目 |
| `czy0729/Bangumi` | 5,956 | 中文真实项目（ACG 客户端），Expo + MobX，长期维护，可看真实代码组织 |
| `CherryHQ/cherry-studio-app` | 3,929 | Cherry Studio 移动版，Expo 做的 AI 助手 App |
| `roninoss/create-expo-stack` | 2,572 | CLI 脚手架，含 Supabase/Firebase 选项 |
| `mmazzarolo/react-native-universal-monorepo` | 1,722 | 多端 monorepo 方案 |

**前端小结：** 采用 obytes 的分层（`app` / `features` / `lib` / `components`），但**做减法**——去掉 i18n、E2E、husky 这些个人项目暂时用不上的部分。

## 3. 后端：生产级范式

### 3.1 `wassim249/fastapi-langgraph-agent-production-ready-template` — 2,675★

AI 服务后端的生产级模板。目录结构：

```
app/
├── api/v1/          路由层，带版本号
├── core/            核心设施
│   ├── config.py        配置与密钥
│   ├── cache.py         缓存
│   ├── limiter.py       限流
│   ├── logging.py       日志
│   ├── metrics.py       指标
│   ├── middleware.py    中间件
│   ├── observability.py 可观测性
│   └── prompts/         提示词管理
├── models/          ORM 模型
├── schemas/         Pydantic 校验
├── services/        业务逻辑
├── utils/
└── main.py
```

**`core/config.py` 是本次调研最有价值的后端代码**，三个做法值得照搬：

**① 分环境 .env 优先级链**

```python
env_files = [
    f".env.{env}.local",   # 最高优先
    f".env.{env}",
    ".env.local",
    ".env",                # 兜底
]
```

**② 环境感知的自动覆盖**——同一套代码，不同环境自动切参数：

| 环境 | DEBUG | LOG_LEVEL | 限流 |
|---|---|---|---|
| development | True | DEBUG | 1000/天 |
| staging | False | INFO | 500/天 |
| production | False | WARNING | 200/天 |
| test | True | DEBUG | 放宽 |

**③ 密钥强度校验，启动即失败**——拒绝空值、短于 32 字符、以及各种占位值：

```python
WEAK_JWT_SECRET_KEYS = {"", "changeme", "change_me", "your-jwt-secret-key", ...}

if len(secret) < 32:
    raise RuntimeError("JWT_SECRET_KEY must be at least 32 characters long")
if secret.lower() in WEAK_JWT_SECRET_KEYS:
    raise RuntimeError("JWT_SECRET_KEY must be a strong random value, not a placeholder or default")
```

这一条直接对应 `AGENTS.md` 第 4 节的密钥红线——**不是靠人记住别写死，而是让程序在启动时直接拒绝**。

其他可借鉴点：按端点细分限流（chat 30/min、login 20/min）、结构化日志（json/console 双格式）、缓存按"host 是否配置"决定启用（可选依赖不强制）。

### 3.2 Node 生态：没有高星模板

检索 "nodejs typescript backend starter production" 等关键词，返回 54 个结果，**最高 star 仅 40**，且多是一人项目、近期创建、无 issue 无讨论。

**这是个有价值的负面结论：** Node 后端领域没有形成公认的"模板"，社区习惯直接用框架本身（NestJS / Fastify / Hono）自己组织。所以选型应该看**框架**的成熟度，而不是找 starter。

命中的低星模板里，出现频率最高的技术组合是：`Express/Fastify + TypeScript + Prisma + PostgreSQL + JWT + Zod + Docker`。

## 4. 多模态识别：没有可抄的

| 仓库 | ★ | 说明 |
|---|---|---|
| `armanchinai/GarmentRecognitionAPI` | 5 | Flask + Azure 视觉，识别衣物，2024 年后无更新 |
| `will-sh/vlmbox` | 1 | llama.cpp 本地 VLM 服务 |
| `nishi-0212/alt-text-api` | 0 | FastAPI + VLM 生成 alt 文本 |

**结论：视觉识别服务化这块几乎没有成熟开源项目**（推理成本高，开源难以持续）。现实路径只有一条——**调云端多模态 API**，后端负责协议转换与结构化输出。

架构范式（综合各模板的做法）：

```
App 上传图片
  → 后端接收（multipart 或 base64）
  → 调 VLM API（带结构化输出约束）
  → 用 zod/pydantic 校验模型返回
  → 校验失败则重试或降级为文本识别
  → 返回稳定结构给 App
```

## 5. 数据抓取：有成熟框架，但我们用不上

| 仓库 | ★ | 语言 | 定位 |
|---|---|---|---|
| `D4Vinci/Scrapling` | 83,750 | Python | 自适应抓取框架，抗反爬 |
| `scrapy/scrapy` | 64,486 | Python | 通用爬虫框架 |
| `gocolly/colly` | 25,529 | Go | Go 生态爬虫 |
| `projectdiscovery/katana` | 17,573 | Go | 爬取+蜘蛛 |
| `crawlab-team/crawlab` | 12,277 | Go | 分布式爬虫管理平台（中文） |
| `code4craft/webmagic` | 11,678 | Java | Java 爬虫框架 |
| `Boris-code/feapder` | 3,739 | Python | 中文爬虫框架，内置调度+监控+断点续爬 |

**判断：** 这些都是为"海量页面、分布式、抗反爬"设计的。看光光只需要抓 **2–3 个政府网站的固定页面、每天几次**，引入任何框架都是过度设计。

但 `feapder` 的三个设计思想值得借鉴到自建抓取里：

1. **断点续爬**——抓取失败记录位置，下次接着来
2. **监控报警**——连续失败要能发现（否则价格静默过期，用户看到的是旧数据）
3. **数据去重**——同一期数据不重复入库

## 7. 完整开发流程（对照 obytes 的 `scripts`）

把 obytes 的脚本拆开看，一个成熟 App 的流程是这样的：

| 阶段 | 做法 | 看光光是否采纳 |
|---|---|---|
| 环境准备 | Node + Expo CLI，`.env` 分环境 | ✅ 采纳 |
| 开发 | 文件路由 + features 分域 | ✅ 采纳 |
| 本地质量门 | `lint` + `type-check` + `test` 合成一条命令 | ⚠️ 精简采纳（先 lint + 自测脚本） |
| 提交规范 | husky + commitlint + lint-staged | ⏸️ 暂缓（单人项目） |
| 构建 | `eas build --profile development/preview/production` | ✅ 第二阶段采纳 |
| 真机调试 | dev-client / Expo Go | ✅ 已可用 |
| 端到端测试 | maestro | ⏸️ 暂缓 |
| 后端部署 | Docker + 环境变量注入 | 待定 |

## 8. 对看光光的六条启示

1. **前端抄 obytes 的分层，不抄它的重量。** 四层结构（app/features/lib/components）保留；i18n、E2E、husky 等个人项目暂不需要。
2. **请求层要"薄"。** axios 实例 + baseURL，其余交给 react-query。不要自造大而全的 request 封装。
3. **环境变量要在项目早期就分层。** 前端 `EXPO_PUBLIC_*`，后端 `.env.{env}` 优先级链。晚做改造成本高。
4. **密钥校验要程序化，不靠自觉。** 照搬 config.py 的"启动时拒绝占位密钥"，把 `AGENTS.md` 的密钥红线变成可执行约束。
5. **识别只能调云端 API，且必须有降级路径。** 后端收图→调 VLM→结构化校验→失败降级，四步一个都不能省。
6. **抓取不要上框架，但要抄它的三个思想**：断点续爬、失败报警、数据去重。
