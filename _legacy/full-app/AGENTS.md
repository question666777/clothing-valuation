# AGENTS.md — 项目开发指令

> 本文件是 AI 助手在本项目中必须遵守的开发规范。每次开发前先读本文件和 `PRD.md`。
> 版本：v0.20（2026-09-27），随项目演进持续更新。

---

## 1. 项目目标

手机 App：用户拍照或上传物品信息 → AI 识别 → 按**五段模型**估算真实价值区间 → 与实际售价对比，辅助购物决策。

### 1.1 第一级：五段模型（公式以此为准）

```
真实价值 = 材料成本 + 加工成本 + 设计成本 + 品牌溢价 + 允许溢出价值
```

### 1.2 第二级：钱花在哪（必须摊开给用户看）

产品的核心卖点是"看得明白钱花在哪"，**只给五个总数就是没做到**。每段必须能下钻到子项：

| 第一级 | 第二级子项 |
|---|---|
| 材料成本 | 主料（面料）· 里料/填充 · 辅料（拉链/纽扣/线/衬） · 五金 · 吊牌包装 |
| 加工成本 | 裁剪排料 · 缝制 · 后处理（绣花/印花/水洗） · 整烫 · 质检包装 |
| 设计成本 | 打版 · 样衣 · 设计稿/买版 |
| 品牌溢价 | 品牌营销分摊 · 授权/加盟 · 门店陈列 |
| 允许溢出 | 运费 · 仓储 · 销售人工 · 平台佣金 · 税费 · 退换货损耗 |

**子项与公式的关系（硬约束）**：

- 材料成本 / 加工成本 / 设计成本：**子项求和 = 第一级**。子项缺数据时该子项留空（显示"未计入"），**不许填 0 假装算过**
- 品牌溢价 / 允许溢出：保持**加成式**（前序项 × 费率），不用子项求和 —— 它们本质是"加价"不是"成本项"，拆成子项会假装精确
- 子项变更**不得影响**第一级公式形状；新增子项只是给对应第一级加一个加数

### 1.3 用户只填一个部位：面料（2026-09-27 改口径，硬约束）

数据层按部位分条，但**界面只让用户答一个问题：这件衣服的面料是什么成分**。

```
materials: [
  // ① 用户填的（界面唯一输入项）
  { part: 'shell', label: '面料', amount: 220, unit: '克',
    fibers: [ { fiber: 'cotton', tier: 'grade_3128B', pct: 100 } ] },
  // ② 系统按品类补的（config.autoMaterialInputs，界面只汇报不可编辑）
  { part: 'lining',  label: '里料', amount: 120, unit: '克', fibers: [ { fiber: 'polyester', pct: 100 } ] },
  { part: 'filling', label: '填充', amount: 180, unit: '克', fibers: [ { fiber: 'down', pct: 100 } ] }
]
```

- **用户的信息源只有水洗标，而他只认得出"面料"那一行。** 里料是什么纤维、充绒多少克，
  标签上要么没写、要么写了也没人注意。把这些做成输入项，结果不是"填得更全"，
  而是**用户随手挑一个凑数** —— 把估价建在假成分上，比我们自己按行业常见值估更坏。
- **哪些部位存在，由品类决定，不由用户决定**：依据 `UNIT_WEIGHT.byCategory` ——
  表里有这个部位就说明这类衣服通常有它（羽绒服有填充、T 恤没有里料）；
  没有的**不生成**，不是"按 0 计入"，而是这件衣服压根不存在这一项。
- **补齐的档位必须走 `getDefaultTierKey`（取中位），不许手填顶格档**。
  羽绒各档价差 167%，标签上没写绒子含量就不许按顶格算。
- **水洗标读到里料 / 填充时以标签为准**（法定标注 > 行业常见值）：界面不做成输入项，
  但解析结果要存下来交给配置层用（`labelParts`）。
- **补齐的部位必须逐条汇报**：界面要写清"这几块钱是替你估的、依据是什么、算进去多少"。
  "钱从哪来"不能说成"你不需要知道" —— 不说，用户没法判断这个数可不可信。
- 组装收在 `config.autoMaterialInputs()` + `config.toValuationMaterials()`，
  **界面不许自己拼**（漏一个部位会被逐级放大成系统性低估，实测漏辅料低估 15%）。
- 数据层仍然支持多部位 + 同部位内混纺百分比 —— 只是**不再由界面要**。
- 混纺部位单价 = Σ(成分占比 × 该纤维单价)，**这是近似**：混纺本身有加工溢价，加权平均会低估。按部位标注"加权估算"
- **成分百分比之和必须凑齐 100%（±1% 容差），且必须在三处同口径执行**（2026-09-27 落地）：
  1. **配置层定价**：合计不齐 → 该条用料 `degraded`，**不给单价**。不齐时加权单价必然错
     （填 80% 就等于按八折出价），老实现照算且不报错 —— 典型静默错值
  2. **界面实时提示**：每条用料显示"成分合计 X%"，不齐时红底醒目
  3. **提交拦截**：不齐时点「估算真实价值」**不跳转**，提示指到第几条
  - 容差只有一份真源：`config.PCT_TOLERANCE`，界面从它取，**各处不许写死数字**
    （写死会出现"界面说合格、配置层判不合格"的幽灵问题）
  - **不足 100% 不许静默补齐**；**取不到价的成分计入"声明合计"**，否则「亚麻 50% + 棉 50%」
    会被误判成"只填了 50%"
- **必须给「其他纤维 / 未标明」这个出口**（`config.OTHER_FIBER`）：GB/T 29862 允许两种以上各 ≤5%
  且合计 ≤15% 时集中标为"其他纤维"。它**计入成分合计但不参与定价**，单价因此偏低，
  这个偏差必须显式警示 —— 没有这个出口，用户为了凑 100% 只能瞎填一个纤维，那是更坏的结果
- **有价就必须在界面上看得见"多少钱、谁发布的、哪一期"**（2026-09-27 补）。
  数据层每条都带 `source` + `period` 全绿，不等于用户看得到 —— 纤维的单价与出处曾经只塞在
  `FIBER_OPTIONS.sub` 里，而 `picker` 只渲染 `label`，那个 `sub` **从头到尾没有任何模板引用过**。
  **"数据齐全"和"用户能核对"是两件事**，界面层必须单独守一条。取不到价的档要如实写"暂无权威报价"，
  不能留空 —— 留空在界面上就是整行消失，用户看到的是"这条成分凭空没了"，而不是"它没有价"
- 普通用户不知道自己衣服用了几米布 → 按品类给**典型单耗（米/件）**作默认值，用户可覆盖；不许让"用量"变成必填空
- **单位体系必须显式换算，跨单位不许裸算。** 纤维原料价一律按**千克**发布（棉花信息网、羽绒信息网…），
  而用户填的用量是**米** —— 中间必须有**克重 × 幅宽 → 每米重量**这座桥（见 5.5）。
  没有桥就会 `17.37 元/千克 × 1.6 米 = 27.79`，**不报错、不降级、静默给出一个没有物理意义的数** —— 比缺数据更危险
- **用户能称的是「整件衣服有多重」，称不出"这件衣服的面料单独用了多少克"**（2026-09-27 补，硬约束）。
  所以界面上不许出现「用量」这种词 —— 它指什么？面料用量、里料用量、还是整件？用户答不上来，
  只能随手填一个数，而那个数直接决定材料成本。**用户唯一能自己验证的用量输入就是整件重量**：
  拿秤一放就有数。界面只问他这个，各部位克数由 `config.distributeByTotalWeight()` 等比换算
  （以该品类各部位**常见用料重量的合计**为基准做等比缩放，一件 480 克的厚外套与一件 300 克的
  薄外套，各部位按同一比例放大缩小）
  - **不填也能算**：回落本类常见值，**行为与加这一项之前完全一致**（不是"按 0 计入"）
  - **口径差异必须说出来**：用户称的整件重量含拉链、纽扣、衬等辅料与五金，而 `UNIT_WEIGHT`
    记的是**用料**重量 —— 两者不严格相等。所以不许造"各部位之和 = 整件重量"的假等式，
    要把基准克数与倍数写进界面（`totalWeightNote`），见 7.7
  - **换品类时整件重量不许被清掉**：衣服还是那件，重量不会因为改了个品类就变
  - 用户手改过某个部位的克数（`weightTouched`）→ 以用户为准，不再被整件重量覆盖

### 1.4 品牌是逐品牌查，不是四个档位（硬约束）

现在的 `BRAND_TIERS` 四档（无品牌/普通/知名/奢侈）是**兜底用的粗分类，不能当数据源**。
优衣库和太平鸟都落在"普通品牌"，加价倍率差一倍以上。要求：

- 建 `config/brands.js` **品牌库**，**每个品牌逐条带出处与期次**；品牌溢价与设计费率都从品牌记录取
- 品牌记录的**粒度是「品牌 × 系列」**，不是品牌：优衣库基础款 vs U 系列、波司登主牌 vs 登峰，
  加价倍率不在一个量级。系列查不到时才回落到品牌级
- **品牌溢价率不手填**，由官方毛利率派生：`加价倍率 = 1 / (1 − 毛利率)`（见 5.2）
- 查不到的品牌 → 回落到档位粗分类，**必须标 `estimate` 并在界面明示"这是按档位估算的"**

详细需求以 `PRD.md` 为准，两者冲突时先向用户确认，不要自行取舍。
**成本口径与常见遗漏项见第 9 节 —— 那节是硬性红线，不是建议。**

### 1.5 材料与品牌按品类分列，但只排序不过滤（2026-09-27 新增，硬约束）

「有些牌子只做衣服，有些只做别的，不能一概而论」—— 这是事实，不是偏好。
波司登 57.2% 的毛利率来自**羽绒服业务**，把它摆在要给 T 恤估价的人面前，
他要么以为我们在乱推荐，要么挑中了、拿一个羽绒服口径的倍率去估 T 恤。
材料同理：把「全棉府绸（衬衣料）」放在要做羽绒服的人的下拉里，只会让他多犹豫一次。

- **数据层**：`config/fabric.js` 的 `FABRIC_CATEGORY`、`config/brands.js` 的 `BRAND_CATEGORY`。
  **每条面料、每家品牌都要登记** —— 漏登记的会被当成"全品类适用"，等于白分
  （快时尚 / 基础款本身就是全品类，登记为 `categories: null`）
- **品牌还要写 `focus`**（一句话业务构成）。有些品牌的部分业务不在本模型范围内，
  必须写明 —— 例如爱马仕的皮具箱包不属于"衣物"，不写用户会以为这个倍率能套到包上
- **判据只此一份**：取值一律走 `config.groupByCategory(items, categoryKey)`，
  界面不许自己写一遍 `filter`
- **只排序分组，不许过滤**。品牌跨品类卖货是常态（波司登也出过 T 恤），
  硬过滤会让用户找不到自己那件衣服对应的选项，还以为是我们的库太差 ——
  那比"列表长一点"糟得多。默认只显示"适合本类"，另给一个"显示全部"的入口
  （`brandScopeOnly` / `fabricScopeOnly`）
- **换品类时，面料 / 品牌的选中项必须按 key 搬过去**（`indexOfKey`）：
  列表一重排，同一个下标指向的就不是同一家品牌、同一块布了。搬不到 → 展开全部再找；
  再找不到才回落，且**必须说出来**。沿用旧下标 = "用户明明选的波司登，切个品类悄悄变成安踏"，
  而且是静默的
- 三条路径（手动切品类 / 按商品名识别出品类 / 切换展开范围）共用 `planCategoryChange()`
  与 `onToggleBrandScope()`，**不许各写一份**（见 7.7 第 3 条的教训）

## 2. 技术栈约定

- 载体：**微信小程序为先，手机 App 为最终目标**（2026-09-27 调整）。
  两端的界面层各写一套，`config/` 与 `core/` 是**同一份代码**（见第 4 节的单向同步规则）
- 小程序侧：原生小程序（WXML / WXSS / JS），代码在 `/miniprogram/`。
  **开发者工具导入的目录必须是 `miniprogram/`，不是仓库根**（2026-09-27 实测踩过）：
  仓库根的 `app.json` 是 Expo 的配置，**没有 `pages` 字段**，从根目录导入会直接报
  `Error: app.json: pages 不能为空`。`miniprogram/` 自包含（自带 `app.json` /
  `project.config.json` / `sitemap.json`，所有 `require` 都在目录内解析）
- `miniprogram/project.config.json` 的 `appid` 已是真实值 `wx1c0cc0e18de4899c`。
  基础库版本由开发者工具「详情 → 本地设置」决定（会随工具升级变动，**不要在文档里写死**）；
  功能上只硬性要求 **≥ 2.27.0**（VisionKit OCR 门槛）
- App 侧：React Native + Expo（SDK 57），项目根即 Expo 工程根；当前**原地保留、暂不维护**
- 小程序服务类目：**工具 → 报价/比价**（官方定义为"商品价格展示、价格对比服务"，官方示例即"各品牌汽车价格展示"）。
  个人主体可注册、免费、**无资质要求**。类目必须与实际功能匹配，否则审核会被打回
- 物品识别：多模态大模型 API，**必须经服务端中转**（前端直连会让 Key 随包分发）。
  小程序对此**没有退路** —— `wx.request` 只能请求已在小程序后台配置白名单的 HTTPS 域名，且域名必须已备案
- **例外：端上 OCR 不涉及 Key、不出网**。水洗标文字识别走微信 VisionKit（`wx.createVKSession`），
  **直接在端上跑，不需要服务端、不需要备案域名**（见 7.1）。这条链路不算"识别必须走服务端"的违例
- 估价数据：抓取政府价格监测网站与公开指数；抓取只能在服务端做
- 价值计算：独立模块实现，公式与系数集中管理，**禁止把系数写死在业务代码里**

## 3. 开发原则（重要）

1. **MVP 优先**：只做 PRD 第 4 节列出的核心功能，不提前实现第 5 节的迭代功能
2. **小步验证**：每个功能做完先能跑通，再优化；不接受一次性交付大块未验证代码
3. **留扩展空间**：项目处于早期，需求会变。代码结构要允许换大模型、换数据源、调公式，但不要为假想需求过度抽象
4. **不确定就问**：PRD 中标记【待定】的事项，遇到依赖时先向用户确认，禁止自行假设后闷头实现
5. **识别可修正**：AI 识别结果必须经用户确认/修正后才进入估价流程
6. **不许编数字**：任何进入计算的价格/费率都必须有出处或明确标为估算，见第 5 节

## 4. 代码规范

- 语言：中文注释和提交信息；标识符用英文
- 注释：默认不写注释，仅在"为什么这么做不直观"时写一行
- 价值计算模块：`/core/valuation/`，对外只暴露 `estimate(itemInfo) → priceRange` 一个主入口；该层为纯计算，不读配置、不碰网络
- 配置与系数：集中在 `/config/`（已建 `coefficients` / `fabric` / `brands` + `index` 取数口，2 个待建）
  - `fabric.js`（**已建**）：`FIBERS` 纤维规格档表（棉按等级 / 羽绒按含绒量×绒种 / 生丝按 A 级 / 羊绒按细度）
    + `FABRICS` 面料表（带成分声明）+ `AUXILIARY_RATIO` 辅料比例 + `AUXILIARY_ITEMS` 辅料条目
    + `UNIT_WEIGHT` **典型单件用料重量（克/件，品类 × 部位）** + `FABRIC_WEIGHT` 典型克重（g/㎡）
    + `FABRIC_WEIGHT_KNOWN` 已公开规格 + `PENDING_FIBERS` 缺源登记 + 价格源快照。
    **每条必须带 source + period + grade**
  - 两张重量表别混：`UNIT_WEIGHT` 是**克/件**（界面默认值，主路径用），`FABRIC_WEIGHT` 是**g/㎡**（换算桥用），
    见 5.5。**为什么两条路**：成衣重量可称量、米数不能，所以主路径让用户填克数
  - 单位换算只此一处：`config/index.js` 的 `convertAmountToKg()` / `resolveWeightSpec()` / `listMaterialParts()`。
    界面与 core **都不许自己乘一遍** —— 那样就有两份换算，迟早不同步（见 5.5）
  - `brands.js`（**已建**）：`BRANDS` 品牌库（逐品牌逐系列：毛利率、期次、出处）+ `INDUSTRY_BENCHMARK`
    板块基准 + `REJECTED_BRANDS` 口径不明拒录名单。**加价倍率与溢价率由毛利率派生，禁止手填**
  - `coefficients.js`：品类加工费、设计费率、溢出比例、区间半宽 + 档位兜底表
  - `breakdown.js`（**待建**）：第二级子项定义表（见 1.2），每个子项声明 `key / label / unit / 数据等级 / 出处 / 是否必填`
  - `loss.js`（**待建**）：损耗与遗漏项系数（面辅料损耗率、次品率、退换货率、售罄率、检测费分摊等，见第 9 节）
- **缺价格时要留空，不许填 0 或估一个数**：`unitPrice: null` + `grade: 'missing'` + `reason`，
  代码走降级并把原因带给界面。典型单耗（米/件）在补到权威出处前**必须留空**（`UNIT_CONSUMPTION._pending`）
- 材料层：`materials` 是**数组**（见 1.3），支持多部位 + 混纺成分；`core/valuation/` 不得假设单条用料
- 品牌层：系数一律经 `config/brands.js` 解析（见 1.4），**业务代码不许出现品牌名硬编码**
- 第二级子项与第一级的求和关系写在校验脚本里（`scripts/verify.js`），**不许靠人眼看是否对得上**
- 界面层：`/src/`，只做展示与交互，**不写业务公式**，所有系数一律从 `/config/` 读
- 路由层：`/app/`（expo-router 文件路由），**只做路由与参数传递**，界面实现放 `/src/screens/`
- 视觉常量：颜色/间距/字号/圆角一律从 `/src/theme.js` 取，**禁止在页面里写死色值与间距**
- 图标资源：`/assets/`，由 `scripts/build-icons.js` 生成，**不要手工替换**（脚本会重画品牌渐变底）
- 识别层：`/services/`，对外契约稳定，换数据源不改调用方
- 抓取层：`/server/`，**服务端专用**（只用 Node 内置模块，零第三方依赖）。
  小程序不能跑抓取（`wx.request` 只认已备案白名单域名），所以这个目录
  **永远不同步进 `miniprogram/`** —— 用目录划平台边界，`SYNC_DIRS` 只有 config/core/services。
  主入口 `node server/fetch-prices.js`（`npm run prices`）：抓取 + 与配置现值对拍 + 出报告，
  **只报告、不改配置**（改价格必须同时改 source 与 period，得人确认）
- 密钥管理：API Key 禁止硬编码进代码，禁止提交到仓库

### 4.1 小程序侧的文件归属（v0.7 新增，硬约束）

`/miniprogram/` 下同时存在**生成物**与**手写文件**，两类规则完全不同，混了就会出问题：

| 路径 | 性质 | 能不能手改 |
|---|---|---|
| `miniprogram/config/`、`core/`、`services/` | `scripts/sync-miniprogram.js` 从项目根**单向生成** | **禁止** |
| `miniprogram/styles/theme.wxss`、`styles/theme.js` | 从 `/src/theme.js` **单向生成** | **禁止** |
| `miniprogram/pages/`、`components/`、`app.js`、`app.json`、`app.wxss`、`project.config.json` | **手写** | 可以，这是界面层 |

- 改真源后必须重跑 `npm run sync:mp`（或 `node scripts/sync-miniprogram.js`）
- **同步必须保持目录层级一致**：`core/valuation/index.js` 里写的是 `require('../../config/index.js')`，
  靠这份相对关系原样成立。**不许把它改成小程序专用路径** —— 那就等于维护第二份公式
- 为什么必须同步：小程序**只能引用自己目录内的文件**，无法 `require` 项目根的任何东西
- 视觉常量：WXSS 用 `styles/theme.wxss` 的 CSS 变量（`var(--color-primary)`），
  页面 JS 需要动态取色时用 `styles/theme.js`；两处都从 `src/theme.js` 生成
- **可点元素的热区 ≥ 40px（硬约束）**。凡是挂了 `bindtap` / `catchtap` 的类，盒子高度
  必须撑到 40px 以上。11px 纯文字 + 零 padding ≈ 16px 高，开发者工具把 375px 宽的模拟器
  缩放显示后只有十来个像素，**就是点不中** —— 表现成"有些东西点不了"。
  想只撑热区不动视觉？用 `min-height` + 负 `margin` 抵消（见 `.line__del`）。
  由 `verify-miniprogram.js` 第 7 组按 WXSS 声明估算并卡限
- **"点了没反应"有三个成因，都要守**：① 热区太小（纯样式，第 7 组）；
  ② 处理函数抛异常（纯逻辑，第 8 组 = `scripts/smoke-page.js`）；
  ③ 绑定名写错 / 方法删了而 wxml 没跟着改（静态可查，第 10 组）。

- 小程序侧契约由 `node scripts/verify-miniprogram.js` 守（工程完整性 / 组件声明齐全 /
  CSS 变量都有定义 / **没有绕过主题写死的色值** / 同步无漂移 / 两端估值结果逐位相同 /
  可点热区下限 / 页面交互冒烟 / 占比口径单一真源 / **事件绑定名都存在**）
- 一键跑两端：`npm run verify:all`；单独跑页面交互冒烟：`npm run smoke:page`
- 效果预览：`npm run preview` 生成 `preview/miniprogram-preview.html`，
  **不用装开发者工具**就能看三页效果（估价 / 结果 / 我的，登录页已移除）。
  里面每个数字都从 `/config`、`/core` 实算，
  **禁止手敲数字** —— 预览与实际脱节比没有预览更坏

## 5. 数据来源红线（重要）

- **不许凭常识填价格**。任何价格/费率都要满足其一：
  1. 有权威出处 → 必须写明来源机构、URL、数据期、抓取日期
  2. 没有出处 → 必须标 `grade: 'estimate'`，并在界面上如实标注为估算
- 官方数据源（已验证可访问）：
  - 绍兴e价通`jgjg.sx.gov.cn`（绍兴市发改委、柯桥区发改局主办）→ 轻纺栏目，含纺织指数与畅销面料排行榜
  - 商务部商务预报`cif.mofcom.gov.cn` → 指数中心，按月发布柯桥纺织指数
  - 中国棉花信息网`cottonchina.org.cn` → CC Index（3128B/2227B/2129B）、新疆长绒棉 137 级、涤纶/粘胶短纤
  - 中国羽绒信息网`cfd.com.cn` → **羽绒价格按含绒量 × 绒种分 16 档**（GB/T 14272-2021 口径）
  - 中国茧丝绸交易市场`esilk.net`（金蚕网）→ **生丝按 3A/4A/5A/6A 分级**、干茧每周现货报价
  - 内蒙古自治区价格监测和认定中心 → 羊绒收购价（按细度：14.5μm 以下等）
  - 清河·中国羊绒指数（清河县政府，经商务部网站发布）→ 无毛绒/绒条/绒纱，每半月一期
  - **国家标准 GB/T 29862**（纤维含量标识）→ 强制要求公开纤维成分与含量，见 5.1
  - **上市公司定期报告**（沪深交易所公开披露）→ 综合毛利率，用于派生品牌加价倍率，见 5.2
- **价格必须按规格档取，不许按纤维名给一个均价**：同为棉，长绒棉 137 级 26.72 元/kg
  vs 细绒棉 2227B 15.84 元/kg（差 69%）；同为羽绒，90% 白鹅绒 984.45 元/kg
  vs 70% 灰鸭绒 369.01 元/kg（差 167%）。均价带来的误差比模型里其他所有系数加起来都大
- **官方没有「面料名」报价档**：牛仔布、雪纺、摇粒绒、帆布、网眼布这些是**商品名或织法**，
  不是纤维，官方指数里查不到它们的价格。识别到这类词只能**推测成分**再按纤维价算（见 7.2），
  **不许去编一个"牛仔布 28 元/米"**。同理，配置里出现的每个档都必须能追到发布源 ——
  追不到的应当登记在 `PENDING_FIBERS` 里说明"暂无权威出处"，而不是默默消失
- **档位默认值不许取极值**：档位表按从贵到便宜排，取"第一个有价的档"就是默认按顶格算。
  实测虚高：**羊绒 223%、羊毛 264%、棉 69%**（`getDefaultTierKey` 已改为取价格中位）。
  中位是**算法**，不是"行业最常见档" —— 后者没有出处，不许编

### 5.1 「去品牌官网查」到底查得到什么（2026-09-26 查证）

**必须分清两类数据，混为一谈会把方向做错：**

| 要的东西 | 品牌官网能否查到 | 真正的数据源 |
|---|---|---|
| 各部位**纤维成分与含量** | **能，且是强制公开** | 国标强制：耐久性标签（水洗标）必须标；新版国标要求**线上销售页面必须公示成分并与实物一致** |
| 面料/辅料的**采购单价** | **不能**。品牌不公布自己的采购价 | 绍兴e价通 / 柯桥纺织指数（行业大宗成交价） |
| 品牌**加价倍率 / 溢价率** | **不能**。品牌不公布自己的溢价率 | 上市公司定期报告的**综合毛利率**反推（见 5.2） |
| 吊牌价（零售标价） | 能 | 官网 / 官方旗舰店明码标价 |

**结论：品牌官网提供的是「成分」，不是「价格」。** 模型要的是
「成分（官网 / 水洗标）+ 单价（轻纺城 / 纺织指数）」两者相乘，
**不许因为官网查不到价格就退回凭常识填价**。

### 5.2 品牌溢价用年报毛利率派生，禁止按档位一刀切

- 来源：上市公司**年报 / 半年报的「综合毛利率」**（沪深交易所公开披露，逐公司逐期）
- 换算：`加价倍率 = 1 / (1 − 毛利率)` —— 这是**派生值，禁止手填**
- **口径细化（实现时才发现，必须记住）**：这个倍率是「**零售价 ÷ 出厂成本**」的**总倍数**，
  里面已经含了品牌溢价 + 渠道费用 + 利润。所以：
  - `premiumRate = 毛利率 / (1 − 毛利率)` 是**总加价率**，**不等于**模型里的「品牌溢价」单项
  - 直接拿它当 premiumRate 会与「允许溢出」**重复计算渠道费用**
  - 代码里对此 `doubleCountRisk = true` 如实标记，界面必须提示，**这个口径冲突尚未解决**（见 9.1）
- 已核实例（2025H1，广发证券纺织服装行业中报总结口径）：
  - 行业整体 34.8%（纺织制造 18.7% / 服装家纺 50.5%）
  - 分板块：女装 67.7% · 户外体育 55.9% · 家纺 51.6% · 休闲 45.0%
  - 个例：海澜之家 45.99% · 森马 47.81% · 报喜鸟 64.89% · 歌力思 70.91% · 比音勒芬 75.88%
  - 央视口径：大众快时尚 40%+ · 中高端 50~70% · 奢侈品 70%+
- **"同一集团差异巨大"的实证**：波司登 2025/26 财年，主品牌毛利率 **69.1%**、
  雪中飞 **40.9%**（集团整体 57.2%）—— 差 28.2 个百分点。按档位一刀切会把这条信息彻底抹掉。
- **口径警告**：毛利率的分母是品牌方的「营业成本」（面料采购 + 代工费），
  与本模型的「材料 + 加工」**大体对应但不等价**，属近似换算，**必须在界面上说明**
- **禁止**把品牌归到 4 个档位就算完事；档位只是查不到品牌时的兜底，且必须标 `estimate`
- **口径不明的品牌一律不录**。例：LVMH 与 Kering 公开报道只给到"经营利润率"
  （Kering 2025 年 11.1%、LVMH 时尚皮具部门约 22%），与毛利率不是一个口径，混用会系统性低估 ——
  已登记在 `config/brands.js` 的 `REJECTED_BRANDS`，**不许为了凑数混进去**

### 5.3 纤维成分标识的三个坑

1. **强制的是耐久性标签（水洗标），吊牌只是推荐性** —— 所以"引导用户拍吊牌"是错的，
   要拍**水洗标 / 洗唛**。吊牌可以没成分，水洗标必须没有不行。
2. **标称含量有法定允差**：含量 ≤5% 可归入"其他纤维"；≤0.5% 可不计入；
   两种以上各 ≤5% 且合计 ≤15% 时可集中标"其他纤维"；含量 ≤10% 允差 3 个百分点，≤3% 时实际不得为 0。
   → 算混纺加权时按**标称值**算，但要知道成分本身有允差，界面不得宣称"精确"。
3. **纤维名称必须用规范名**（GB/T 11951 天然纤维 / GB/T 4146.1 化学纤维 / GB/T 17685 羽绒羽毛）。
   "云朵棉""冰感丝""恒温羊绒"这类**营销词不是成分**，OCR 读到一律拒绝，不许当纤维名查价。
- 标准版本注意：新版《纺织品 纤维含量标识技术规范》**GB/T 29862-2026** 已发布（2026-07-02），
  官方口径为 **2027-08-01 实施**，替代 2013 版；落地前需再核标准正文（部分来源表述与实施日期不一致）。
### 5.4 抓取与降级（2026-09-27 实测）

**当前仍是打包快照，不是实时值。** 抓取入口已经建好并可跑（`server/`），但**尚未定时化** ——
定时化需要一个能常驻、能发 HTTP 的地方（云函数 / 服务器），本机脚本解决不了"每天自己跑"。

**逐源实测结论（带证据，完整版见 `server/source-catalog.js`）：**

| 源 | 状态 | 说明 |
|---|---|---|
| 中国棉花信息网 | **ready** | 首页静态 HTML 直接带当日全套指数（GBK 编码），无需登录无需接口。已实现自动抓取，覆盖棉三档 + 粘胶/涤纶短纤，**与配置现值逐条对上** |
| 绍兴e价通 | unreachable | curl 与 Node 均 `CONNECT tunnel failed, response 502`，主站 `jgjg.sx.gov.cn` 同样不通。是网络层不可达而非反爬，换出口应重测 |
| 中国羽绒信息网 | partial | JSON 接口已打通，但返回的是进出口**数量**统计，价格类页面未定位 |
| 金蚕网 | partial | 公开 JSON API 已打通（`jqadmin.esilk.net/api/publication-results/?id=N`），但 id=1 是景气指数（0~100 情绪指标）不是生丝元/吨，对应 id 待试出 |
| 商务部商务预报 | js-rendered | 指数中心正文靠 JS 加载，HTML 内无数字，接口未定位 |

**两条教训（本轮实测换来的，别再重踩）：**

1. **首页能抓 ≠ 价格能抓。** 六个站 HTTP 全 200、页面也都拿到了，但第一轮探测的
   「可见价格片段」**全是 0** —— 政府站普遍把数据放在网络层之后（JS 渲染 / 登录墙 / 动态接口）。
   **判定可行性必须下钻到「能不能解析出数字」，不能只看状态码和字节数。**
2. **"官方源可访问"是有环境依赖的。** 绍兴在本机不通，不代表服务器出口也不通，反之亦然。
   正式的可用性判定必须在**将来真正跑抓取的那个环境**里做，本机结论只能当初筛。

**其余口径不变：**

- 只抓公开页面，遵守 robots 协议，控制请求频率（`server/lib/http.js` 内置 600ms 限速 + 固定 UA 标识）
- 抓取失败时估价降级（用打包快照兜底），不允许整个流程崩溃
- **抓不到就如实报告失败，不许填假数**：解析不到的指标进 `missing` 并带原因（见第 5 节红线）
- 所有估价结果页必须展示免责声明："估值仅供参考，不构成购买建议"

### 5.5 计量口径：按克（2026-09-27 改为按克填报）

**问题**：纤维原料价一律按**千克**发布（中国棉花信息网、中国羽绒信息网、金蚕网…），
而用户填的用量原本是**米**。没有换算桥就会 `单价(元/千克) × 用量(米)` ——
这个乘法**语法合法、运行不报错、不触发降级**，但结果没有任何物理意义。

**它比缺数据危险**：缺数据会走降级、界面能看见"未计入"；单位裸乘是**静默给错数**，谁都发现不了。

**主路径：用户直接填克数。** `克 ÷ 1000 = 千克`，**零假设**。
界面默认值取 `UNIT_WEIGHT`（品类 × 部位典型单件重量，全部标 `estimate`），
提示"称一下最准，可直接改"。
理由：**成衣重量是可称量的，米数不是** —— 让用户提供一个他能量出来的数，
比替他假设「克重 × 幅宽」可靠。用户改过的克数**不再被品类切换覆盖**（`weightTouched`）。

**按「米」那条路仍保留，但不是主路径**：桥只有一座，在 `config/index.js`
`convertAmountToKg(amount, unit, spec)`，按 `每米重量(kg/m) = 克重(g/㎡) ÷ 1000 × 幅宽(m)` 换算。
界面与 core **都不许自己乘一遍** —— 那样就有两份换算，迟早不同步。
克重优先级：① 用户实测值 → ② `FABRIC_WEIGHT_KNOWN`（绍兴e价通条目原文已公布的规格）
→ ③ `FABRIC_WEIGHT`（品类 × 部位典型值）→ ④ 部位兜底。

- **克重是物理量，不是价格**，可给行业常见区间中值，但全部标 `grade: 'estimate'`，**不许混进 official**
- 带假设的用料标 `specAssumed: true`，界面**必须把假设值显示出来**并允许改成实测值
- 单耗（米/件）仍然留空 —— 那是另一回事，没有权威出处就不填（`UNIT_CONSUMPTION._pending`）
- `件 / 条 / 个` 与千克**没有换算关系**，返回 `unconvertible: true` 并如实告知，不许硬套一个系数
- 按克填报时 `weightSpec` 必须是 `null`（纯换算无假设），别把估出的克重挂上去误导界面说"这里用了假设值"

### 5.6 纤维覆盖度怎么算「够」（2026-09-27 定）

"面料种类覆盖全了吗"不能凭感觉答，要有判据。**判据不是"价格表里有多少条"，
而是「识别得到的每一种纤维，价格层都必须有落点」。** 因为识别的意义在于能算价 ——
识别命中却查不到价，等于没识别（见 7.2）。分三层，每层都有明确出口：

| 层 | 内容 | 出口 |
|---|---|---|
| 有官方/可核价 | 棉（4 档）· 羽绒（16 档）· 生丝（3 档）· 羊绒（3 档）· 羊毛（5 档）· 涤纶 · 粘胶 | `FIBERS` |
| 识别得到但无权威价 | 亚麻 · 锦纶 · 氨纶 · 腈纶 · 莱赛尔 · 莫代尔 · 醋酸 · 兔毛 · 马海毛 · 羊驼毛 · 丙纶 · PU · 真皮 | `PENDING_FIBERS`（逐条写原因） |
| 国标允许的**非纤维**标注 | 其他纤维 / 未标明 | `OTHER_FIBER`（计入合计、不参与定价） |

合计 **20 种纤维 + 1 个占位**，覆盖 GB/T 11951（天然纤维）/ GB/T 4146.1（化学纤维）
里成衣会遇到的绝大部分。

- **加识别词忘了补登记 → 校验脚本直接红**（`verify.js` 第 15 组「纤维覆盖度」）。
  这条是真踩过的：识别词典收了 16 种、价格层只登记 14 种，**莫代尔与醋酸两头落空**，
  用户看到"识别到了但价格表里没有"，理由还只是兜底那句"该纤维不在价格表中"，说不清为什么
- **规模小是故意的**：不做"把 GB/T 里几十种纤维全补上"。服装用不到的（金属纤维、碳纤维、
  芳纶、维纶）收进来只会稀释维护成本。缺的补法只有一条：**先看官方有没有这种报价档，
  没有就登记缺源，不许顺手填个数**
- **「纤维有价」≠「面料有价」**：官方只按「纤维 × 规格档」报价，没有"牛仔布""雪纺"这种
  面料名的报价档 —— 所以识别只给纤维线索（见 7.2）
- 价格表里每条都带 `grade`；`missing` 是正常状态（如辅料单价全为 null），
  **不许为了让表"看起来完整"而补数**

### 7.1 拍照识别（2026-09-27 实装，不依赖后端）

- **入口是拍水洗标，不是吊牌** —— GB/T 29862 强制公开成分的是耐久性标签，吊牌只是推荐性（见 5.3）
- 链路：`wx.chooseMedia` 拍照 → **微信 VisionKit 端上 OCR** 读字
  （`wx.createVKSession({ track: { OCR: { mode: 2 } } })`，mode 2 = 静态图片；
  frameBuffer 为 RGBA 像素，每像素 4 项；**要求基础库 2.27.0+**，**不需要后端、不需要备案域名**）
  → `services/recognize.js` 的 `parseFiberLabelText()` 解析成分 → 回填用料行
- **为什么没用 GitHub 上的开源方案**：查到的端侧识别项目全是服务端 Python
  （Flask/Gradio/Streamlit + TensorFlow/PaliGemma 等），**没有能塞进小程序运行时的**；
  而 `wx.request` 只能请求已备案并加入白名单的域名，走服务端等于把 MVP 卡在后端上。
  VisionKit 是微信自带的，**现在就能用**
- OCR 不可用时（基础库过低 / 超时 10 秒）**降级到手动敲文字，解析逻辑是同一套**
  （`onParseLabelText` 走同一个 `parseFiberLabelText`），所以这条链路永远可用
- 解析规则（已固化成断言）：
  - **单字纤维名必须认得出**：`"面料：棉100%"` 里的「棉」是单字 ——
    纤维名正则写 `{2,}` 会把最常见的那种纤维整个漏掉，必须 `{1,}` 并把部位词加进噪声词
  - **营销词一律拒绝**："云朵棉""冰感丝""恒温羊绒"不是纤维名，不当成分查价
  - 羽绒段里的百分比是**含绒量**不是成分占比（"白鹅绒 95%" → `white_goose_95` 档，向下取整档）
  - 成分合计不足 100% **如实标出，不静默补齐**
  - 非国标写法明确失败并给填写示例，**不瞎猜**
  - 解析出的成分若价格表里查不到（亚麻、锦纶等），**列出告知用户，不静默丢弃、不填 0**
- 识别结果**可修正**（第 3 节原则 5）：回填后仍可在用料行里改

### 7.2 商品名识别：给「纤维线索」，不给「面料档」（2026-09-27 修）

用户填了商品名（"牛仔外套""摇粒绒卫衣"）时，`recognizeByText()` 会预填用料。

**老实现是错的，而且错得没被发现**：它产出 **面料档 key**（`denim` `canvas` `chiffon`
`knit_rib` `cotton` `polyester` …），16 个里 **10 个在 `FABRICS` 里根本不存在** ——
而落空的恰好全是商品名里最常见的词，等于识别命中反而等于没识别。

**根因不是"缺几条数据"，是口径**：官方报价只按「**纤维 × 规格档**」发布，
**没有"牛仔布""雪纺""摇粒绒"这种面料名的报价档**（见 5.1）。
所以"补全 10 个面料档"这个方向本身就是编数字。

**修法**：识别表 `FABRIC_HINTS` 改成产出**纤维线索** ——

| 商品名里的词 | 推测纤维 | 依据 |
|---|---|---|
| 牛仔 / 帆布 | 棉 | 这两类基本都是纯棉或棉涤 |
| 摇粒绒 / 抓绒 / 网布 / 速干 / 雪纺 | 聚酯纤维 | 基本是涤纶（雪纺也可能是真丝，提示里说明） |
| 真丝 / 羊绒 / 亚麻 / 真皮 / 羽绒 | 对应纤维，且面料档真实存在 | 同时给 `fabricKey` |
| **针织 / 罗纹 / 加厚 / 毛圈 / 混纺** | **不猜** | 织法、厚度、没给比例的混纺**说明不了成分**，猜错会把估价建在假成分上 |

规矩：

- `fiberHints` 是**推测，不是事实**。界面必须标明"按商品名推测，请核对"，**不许当成识别结果直接算价**
- `fabricKey` **只在真实存在于 `FABRICS` 时**才返回，否则留空 —— 幽灵 key 会让界面静默落空
- 推不出成分时必须给 `hintNote` 说明原因（**不许静默返回空**）
- 羽绒只识别到纤维、判不出含绒量时，如实提示档位价差（70% 与 95% 差 167%）
- **不覆盖用户定过的成分**：用料行带 `fibersTouched`，水洗标回填与手工编辑都会置位，
  商品名推测**只在没置位时**才填 —— 商品名说不过水洗标
- 守这条的断言（`verify-miniprogram.js` 第 6 组，8 条）：
  静态查线索表里的 `fabricKey`/`fiber` 是否都能在配置层找到（或有 `PENDING_FIBERS` 登记）、
  动态拿 8 个真实商品名跑一遍、反向查"不猜也必须给理由"

**识别的三类输出都必须被消费**（2026-09-27 补）。`recognizeByText()` 返回
`category` / `fiberHints` / `brandTier`，前两个接了，**`brandTier` 曾经被界面整个丢掉**。
它决定设计费率：奢侈档 **0.60** vs 普通档 **0.12**，**差 5 倍** —— 丢了它，一条奢侈品牌的估价
会按普通品牌算出来，不报错、不降级、数字看着还挺正常。规矩：

- 商品名里出现**品牌正名**（爱马仕 / 海澜之家 / 李宁 / H&M）→ 预选该品牌，用年报毛利率，
  并提示"这是预选、请核对"（与成分预填同构：识别结果永远只是预填）
- 品牌库对不上的（香奈儿 / LV / Gucci… 库外品牌，没有年报可查）→ **档位信息照样有效**，
  存进 `brandTierGuess` 作为兜底传入估价，界面必须写明"按该档位估算，不是年报数据"。
  **不做成输入项** —— 用户不知道什么叫"品牌档位"，问了只会得到瞎选
- **匹配只能用品牌正名，不碰 `aliases`**：`aliases` 里有 `HLA`，而 `ralphlauren` 恰好含
  `hla`（ra-lp**hla**-uren）—— 拿别名做子串匹配，"Ralph Lauren 衬衫"会被认成海澜之家。
  这是项目踩过的那个坑，所以另立 `config.findBrandMention()`（输入是**商品描述**），
  与 `findBrandByName()`（输入是**品牌名本身**，模糊匹配要求别名 ≥4 字）分工不同，**别混用**
- **换品类要刷典型克数，两条路径必须共用一份实现**：手动切品类、与"识别出品类"是同一个
  状态变化。各写一遍必然漂移 —— 识别那条就曾经忘了刷，用户输入"羽绒服"后品类换了、
  自动补了填充，面料克数却还停在上一个品类的值上，看着正常、实际对不上

  第 11 组。教训：**数据层全绿 ≠ 用户能核对**，界面层得单独守一条
- **识别规则与面料价格表脱节** —— 根因不在"缺几个面料档"，而在口径：官方只按
  「纤维 × 规格档」发布价格，**没有"牛仔布/雪纺/摇粒绒"这种面料名报价档**，所以补档 = 编数字。
  修法是让识别产出**纤维线索**（见 7.2），落到真正有价的档上
- **所有多档纤维的默认档曾取到最贵那一档**（羊绒虚高 223%、羊毛 264%、棉 69%）——
  已改为按价格排序取中位（`getDefaultTierKey`），并加断言守死。
  **档位仍未定就仍是估算**，界面必须让用户改
- **五段拆解曾漏算辅料，总估值低估 15%** —— 界面把材料交给估价核心时只映射了
  `material.lines`（主料/里料/填充），漏掉 `auxiliaryCost`（辅料）。而 `core` 的材料成本
  是各行求和，且**设计 / 品牌溢价 / 允许溢出全以材料为基数**，少算的 26.27 被逐级放大
  （材料 105.09 → 131.36，总额 1133.25 → **1303.30**）。同时 `PART_META` 里「材料成本」
  的说明明写「面料 + 辅料」，值与文案自相矛盾。
  **修法**：把组装收进配置层 `config.toValuationMaterials(material)`（界面与预览脚本都调它），
  **界面不许自己拼用料数组** —— 那个拼法正是 bug 来源。辅料为 0 时不追加空行，
  否则会被 core 的"有取不到价的用料"判据命中而降级误报。已加 3 条断言守死
- **一部分控件点不中（"有些点不了，比如那个添加成分"）** —— 事件绑对了、逻辑跑起来
  全过、不报错，但 `＋ 添加成分` 写成了一行 `font-size: 11px` 的纯文字 + **零 padding**，
  盒子只有约 16px 高；开发者工具把 375px 宽的模拟器缩放显示后，它在屏幕上只剩十来个像素。
  **对照就是线索**：同一张卡片里「＋ 添加一种用料」是 `.btn`（高 52px）、拍照入口高 64px，
  所以那几个点得中、这个点不中。
  **修法**：所有挂了 `bindtap` 的类撑到 ≥ 40px（`.fiber-add` /
  `.fiber-row__del` / `.alt` / `.fold__edit` / `.chip`）；只想撑热区不动视觉就用
  `min-height` + 负 `margin`。
  **加了三个守卫，因为"点了没反应"有三个成因**：第 7 组按 WXSS 声明估算热区高度卡 40px 下限；
  第 8 组 `scripts/smoke-page.js` 把事件处理函数真跑一遍（抛异常也表现成没反应）；
  第 10 组查 wxml 里绑的处理函数是否真的存在于页面 js（方法删了而模板没改，同样毫无反应）
- **开发者工具报 `app.json: pages 不能为空`** —— 导入目录选成了仓库根。仓库根的 `app.json`
  是 Expo 的配置、没有 `pages`，见第 2 节。**代码没有问题**，换目录即可
- **成分占比没凑到 100% 也照算，等于按缺失比例静默打折** —— 用户填「棉 80%」就只加权
  0.8，单价低了 20%，但既不出错也不降级，界面看上去完全正常；而且这和「缺价纤维被跳过」
  是同一个根：**分母不完整**。修法见 1.3：配置层不平就降级不给单价、界面实时显示合计、
  提交时拦住；并给「其他纤维」出口（国标允许的合法标注）。已加 11 条断言（`verify.js` 第 14 组）
  + 8 条页面真跑用例（`smoke-page.js`）
- **莫代尔 / 醋酸纤维识别得到、价格层两头落空** —— 识别词典收了 16 种纤维，`PENDING_FIBERS`
  只登记 14 种，差的正是这两个；命中的结果不是报错，而是落到兜底那句"该纤维不在价格表中"。
  补登记的**同时**加了第 15 组断言：识别表里每种纤维都必须有落点，以后加词忘补就直接红。
  纤维覆盖度现状见 5.6
- **用料清单是"第 N 种"的平铺长表（2026-09-27 改造）** —— 老界面的模型是"一条用料 = 一行"，
  用户要选部位 → 选计价方式 → 填成分 → 填用量，一条 8 个控件；三四种用料就是一张长表。
  问题不在控件多，在**模型错了**：一件衣服的部位是固定的那几个，不是让用户凭空新增"第 N 种"。
  **修法**见 1.3：改成「面料 / 里料 / 填充 / 辅料 / 五金」的滑动板块，一个部位一屏；
  未填的部位不占地方、点一下带着典型值出现；克重与计价方式从"必填项"降级为
  "系统填好 + 可展开覆盖"。`onAddLine` / `onPartChange` 随之删除（留成死代码就会有人以为还能用）
  - **注意：这一段的方向后来又被推翻**（部位不该出现在界面上），见下面那条留档与 1.3 的现行口径
- **换计价方式时单位没跟着换**（改造时顺手挖出）—— 按面料名是**元/米**，但 `onModeChange`
  只改了 `mode`，`unit` 还留着"克"：界面显示"200 克"而定价按米算。
  与上面「漏辅料」是同一种病 —— **"界面显示的口径"和"实际算的口径"不是一件事**。
  修法：换模式连 `unit` 一起换；从米换回克时把米数重置为该部位的典型克重（米数不能当克数接着用）
- **「按部位滑动板块」被推翻：用户只填面料（2026-09-27 再改）** —— 上一版把部位做成
  5 个滑动 tab（面料 / 里料 / 填充 / 辅料 / 五金），方向仍然错：**用户的信息源只有水洗标，
  而他只认得出"面料"那一行**。里料是什么纤维、充绒多少克，标签上要么没写、要么没人注意。
  把这些做成输入项，得到的不是"填得更全"，而是**用户随手挑一个凑数** —— 把估价建在假成分上，
  比自己按行业常见值估更坏。**修法**见 1.3：界面只留「面料成分」一个输入；
  里料 / 填充由 `config.autoMaterialInputs()` 按品类补（`UNIT_WEIGHT.byCategory` 里有这个部位
  才生成）；水洗标读到的里料 / 填充以标签为准（法定标注 > 行业常见值），但**不做成输入项**；
  系统替用户计入的部位**逐条汇报金额与依据**。
  删掉的东西：`partTabs` / `switchPart` / `onTabTap` / `onDisablePart` /
  `onPanelTouchStart|End` / `buildPartTabs` / `tabIntoView` / `noop` 与对应 WXSS
  —— **留成死代码就会有人以为还能用**（第 10 组会守住这类"模板绑了不存在的方法"）
- **"系统替用户填"不等于"可以不说"** —— 补齐的部位如果只是悄悄计进金额，用户看到材料成本
  从 ¥3.89 跳到 ¥148.86 却找不到原因，只会怀疑整个模型。所以每一条自动计入都要报出
  **部位 + 克重 + 金额 + 依据**（是行业常见值还是照水洗标）。这条与"漏组成项"是一体两面：
  漏算是静默低估，不解释是**静默不可信**

### 7.6 联网与上线门槛（2026-09-27 定论）

**结论：这个小程序运行时零联网 —— 不需要服务器、不需要域名、不需要 ICP 备案。**

怎么确认的（不是推测，是检索）：小程序目录内 `wx.request` / `wx.cloud` / `uploadFile` /
`downloadFile` / `connectSocket` **一处都没有**。全部能力都是本地的：

| 能力 | 靠什么 | 要联网吗 |
|---|---|---|
| 材质 / 面料 / 品牌数据 | 打包在 `config/` 里（几十 KB） | 不要 |
| 五段估价计算 | `core/` 纯函数 | 不要 |
| 拍水洗标读成分 | **微信 VisionKit 端上 OCR**（`wx.createVKSession`） | 不要 |
| 拍照 / 选图 | `wx.chooseMedia` | 不要 |
| 偏好保存 | `wx.setStorageSync`（本机缓存） | 不要 |

**唯一需要网络的一刻：首次下载小程序包、以及版本更新。** 这是微信平台行为，
所有小程序都一样，不是我们引入了网络依赖 —— 与"很多小程序打开就没法用"是两回事
（那些是每次打开都要调后端接口：登录、拉数据、支付）。

**这意味着上线门槛只有"注册小程序账号 + 提交审核"，没有后端工程。** 个人主体可注册，
不需要 ¥688/年的 iOS 开发者账号，也不需要 Mac。

**分界线在哪 —— 一旦做这两件事就跨过去了**：

1. **接多模态大模型做识别** → API Key 不能进包（第 4 节密钥红线），必须走服务端中转 →
   服务端要有域名 + 备案。此时唯一免备案的路是**微信云开发**（`wx.cloud`，腾讯自家域名）。
2. **价格自动更新** → 需要"能定时发 HTTP 的地方 + 定时器"，同样落在这条线上。
   在此之前，价格只能是**打包快照**（见 5.4），更新要重新发版。

**代价（零联网的反面，必须讲清楚）**：界面上的价格是**发版那天抄进去的**，
源更新了不会自动变；用户离线时能用缓存包打开，但首次使用必须联网下载。

### 7.8 本轮已修（2026-09-27 第二轮，留档便于回溯）

1. **界面加「整件衣服重量」，删掉含义不明的「用量」**（见 1.3）。
   换算收在 `config.distributeByTotalWeight()`：以该品类常见用料合计为基准等比缩放。

2. **首页按数据类型重排为四组**：① 这件衣服是什么（物品名称置顶 / 品类 / 整件重量）
   ② 面料成分 ③ 品牌 ④ 多少钱买的。原来的毛病是两类混着摆：名称夹在拍照区和品类之间、

3. **材料与品牌按品类分列**（见 1.5）。新增 `FABRIC_CATEGORY`（18 条）/ `BRAND_CATEGORY`（20 家）

   用户选的波司登悄悄变成安踏。现在一律按 key 搬（`indexOfKey`），搬不到就展开范围再找，
   **不许静默回落**。三条路径（手动切 / 识别出 / 切展开范围）共用 `planCategoryChange()`

## 9. 成本口径与常见遗漏项（硬性红线）

> 这一节存在的理由：五段模型里"材料 + 加工 + 设计"是**出厂成本**，"允许溢出"是**流通成本**，
> 品牌溢价是**定价结果**。三类东西混在一根加法线上，不写清口径就必然算歪。

### 9.1 三条口径红线

1. **口径必须二选一，并在结果页写明**：本模型输出的是"出厂成本口径"还是"消费者到手口径"。
   当前实现把出厂项和流通项直接相加，**跟售价对比时基准不清**，属于已知缺陷。
   建议：默认给**出厂成本口径**为主结论，流通项单列作参考，不要糊成一个数。
2. **品牌溢价不是成本，是价格构成**。它是消费者愿意多付的钱，不是商家花掉的钱。
   把它并入"真实价值"再和售价比，会出现"售价 = 价值，所以永远合理"的自我实现 ——
   奢侈品牌永远不算贵。**品牌溢价必须单列展示，且不得计入"成本底线"。**
3. **"允许溢出由用户定比例"会让结论自证**：用户拖滑块能得出任意结论。
   必须提供一个**固定基准锚**（建议：品类推荐初值下的结果），滑块只作为敏感性参考，
   且界面上要说明"这一项是你自己设的"。

### 9.2 必查遗漏项（当前模型一个都没有）

| 遗漏项 | 归属 | 为什么容易漏 | 现状 |
|---|---|---|---|
| **面辅料损耗率** | 材料 | 用户填的是**净用量**，实际投产要按排料损耗 + 裁坏加放，针织 8~12%、梭织 5~8%、羽绒 10~15% | 缺失，**系统性低估材料成本** |
| **次品/报废率** | 加工 | 返修与报废工时不会被计入加工费 | 缺失 |
| **质检与合规检测** | 加工 | GB 18401（纺织品安全）、GB 31701（婴幼儿）按款送检，几百到几千元/款 | 缺失 |
| **打版费与样衣费摊薄** | 设计 | 版费按款收，投产件数少时每件摊薄极高；现在用固定比例代替，批量小就低估 | 用比例代替 |
| **吊牌/洗标/包装** | 材料 | 单件几毛到几块，看着小，占比 3~8% | 未单列 |
| **增值税** | 溢出 | 报价含税与否直接差 13%，口径不清数字没意义 | 缺失 |
| **平台佣金/流量费** | 溢出 | 天猫约 5%、抖音小店 1~5%，直播另有坑位费 | 缺失 |
| **退换货损耗** | 溢出 | 服装电商退货率可达 30~50%，退回品需重整烫/重包装甚至报废 | 缺失，**服装行业最大隐性成本之一** |
| **库存与季末打折** | 溢出 | 服装售罄率通常仅 60~70%，剩余打折清仓，实际均摊成本被抬高 | 缺失 |
| **资金占用** | 溢出 | 面料备货到回款常 3~6 个月 | 缺失 |

### 9.3 品牌与成分维度的遗漏项

| 遗漏项 | 为什么容易漏 | 后果 |
|---|---|---|
| **同品牌不同系列** | 品牌库里只放品牌名，不放系列 | 优衣库基础款 / U 系列、波司登主牌 / 登峰的加价倍率不在一个量级，混成一个数就全错 |
| **同品牌不同渠道** | 溢价率被当成品牌常数 | 官方旗舰店 / 奥特莱斯 / 直播间 / 代购，同一件衣服价差 2~3 倍 |
| **同品牌不同品类** | 一个品牌只给一个溢价率 | 同一品牌的包与成衣溢价结构完全不同，服装品类尤其不能跨用 |
| **授权 / 贴牌品牌** | 把"牌子"当成质量的证据 | 授权模式下品牌与品质脱钩，吊牌价高但面料可能很次 —— 对"看穿价格"是**反向陷阱** |
| **混纺不是线性加权** | 直接按成分占比做加权平均 | 混纺本身有加工溢价，且不同组分价差越大误差越大，加权平均会低估 |
| **同纤维不同规格** | 价格表只按纤维名分档 | 长绒棉 ≠ 普通细绒棉、美利奴 17.5μm ≠ 普通羊毛、90% 含绒 ≠ 70% 含绒，价差可达数倍 |
| **辅料也有品牌** | 辅料被一个固定比例打包 | YKK 拉链与普通拉链价差 5~10 倍，辅料品牌是"溢价"的一部分，现在完全看不见 |
| **克重 / 单耗** | 认为用户能填出用了几米布 | 用户填不出，且不知道克重；必须按品类给典型单耗兜底，否则材料成本无输入 |
| **成分允差** | 把标称成分当精确值 | 含量 ≤10% 法定允差 3 个百分点，界面不得宣称成分"精确"（见 5.3） |

### 9.4 落地要求

- 上述系数一律进 `/config/loss.js`，**每条标明数据等级**（`official` / `semi` / `estimate`），没有出处的老实标 `estimate`
- 品牌与成分类数据进 `/config/brands.js`（见 1.4、5.2）与 `/config/fabric.js` 的规格字段，**每条带出处与期次**
- 结果页必须能展开看到"哪些项已计入、哪些项因缺数据未计入"，**不许静默省略**
- 每补一个遗漏项，都要在 `scripts/verify.js` 里加一条对照断言
- 不许为了"看起来更准"给未确认的系数编一个像样的数字 —— 见第 5 节
