# 真实价值购物助手 — 产品需求文档（PRD）

> 版本：v0.20（草案，2026-09-27）
> 状态：早期设想阶段，多处未定，标记为【待定】的条目后续迭代确认

---

## 1. 产品定位

一款帮助消费者"看穿价格"的工具。用户在购物前，通过**拍照**或**手动上传物品信息**，App 自动估算该物品的**真实价值区间**，并与实际售价对比，辅助用户判断"值不值这个价"。

一句话定位：**买东西前拍一下，看看它到底值多少钱。**

产品名：**衣物估价**

## 2. 目标用户与场景

- 目标用户：对价格敏感、希望理性消费的普通消费者
- 典型场景：
  1. 逛商场/网购时看到一件商品，想知道它的成本大概多少、溢价高不高
  2. 对比同类商品时，想快速判断哪个更"实在"
  3. 遇到大幅促销，想验证是不是真便宜

## 3. 核心价值模型（五段）

```
真实价值区间 = 材料成本 + 加工成本 + 设计成本 + 品牌溢价 + 允许溢出价值
```

| 组成部分 | 说明 | 数据来源 |
|---|---|---|
| 材料成本 | **多部位用料之和**（面料/里料/填充/辅料/五金），每个部位内部还可以是**混纺** | 纤维**成分**来自品牌官网 / 水洗标（国标强制公开）；**单价**来自政府价格监测网站与纺织指数 —— 两者是不同来源，见下 |
| 加工成本 | 裁剪、缝制等工序价值 | 按品类预设**元/件**加工费（服装加工按件计费，与面料贵贱无关） |
| 设计成本 | 打版、样衣、设计投入 | (材料 + 加工) × 设计费率，费率按**品牌 × 系列**取（白牌抄款趋近 0，奢侈品牌最高） |
| 品牌溢价 | 品牌带来的附加价值 | (材料 + 加工 + 设计) × 溢价率；溢价率由**上市公司定期报告毛利率**派生，**不手填** |
| 允许溢出价值 | 流通成本：运费、人工、销售费用 | **由用户在结果页自行决定比例**，系统只给品类推荐初值 |

输出形式：一个**价格区间**（而非单一数字），并给出五部分拆解，让用户看得明白钱花在哪。
**每一部分必须能下钻到第二级子项**（主料/里料/辅料/工序/打版/运费……），只给五个总数不算做到 —— 详见 `AGENTS.md` 第 1.2 节。

### 3.0.1 成本口径（三条红线，详见 `AGENTS.md` 第 9 节）

1. **口径二选一**：模型算的是"出厂成本"还是"到手成本"，必须明确并在结果页写明（当前实现两者混算，已知缺陷）
2. **品牌溢价不是成本**，是价格构成。必须单列，**不得计入"成本底线"**，否则"售价 = 价值"会自我实现
3. **"允许溢出"由用户定比例会让结论自证**，必须给一个固定基准锚，滑块只作敏感性参考

### 3.0.2 必查遗漏项

当前模型完全没有计入，但都是服装成本的真实组成部分：
面辅料损耗率、次品报废率、质检与合规检测（GB 18401 / GB 31701）、打版与样衣费摊薄、
吊牌洗标包装、增值税、平台佣金、**退换货损耗**、**库存与季末打折**、资金占用。
完整清单与归属段见 `AGENTS.md` 第 9.2 节。

### 3.0.3 用户只填一个部位：面料（多部位在数据层，不在界面）

一件衣服的用料**不是一种**，数据层必须支持：

- **多个部位**：面料 / 里料 / 填充 / 辅料（拉链、纽扣、线、衬）/ 五金 / 吊牌包装
- **同一部位内混纺**：如"80% 羊毛 + 20% 涤纶"，按成分百分比记录，加权算单价（近似，混纺有加工溢价）

**但界面上只让用户答一个问题：这件衣服的面料是什么成分**（2026-09-27 再改，理由见 `AGENTS.md` 1.3）。
用户的信息源只有水洗标，而他只认得出"面料"那一行 —— 里料是什么纤维、充绒多少克，标签上要么没写、
要么没人注意。把这些做成输入项，得到的不是"填得更全"，而是**用户随手挑一个凑数**。

- **哪些部位存在由品类决定**（依据典型克重表）：羽绒服有填充、T 恤没有里料；
  没有的**不生成**，不是"按 0 计入"，而是这件衣服压根不存在这一项
- **系统替用户计入的部位必须逐条汇报**：部位 + 克重 + 金额 + 依据。
  只把钱悄悄加进去，用户看到材料成本跳变却找不到原因，只会怀疑整个模型
- **水洗标读到的里料 / 填充以标签为准**（法定标注 > 行业常见值），但不做成输入项
- 克重 / 辅料比例 / 品牌档同样由系统给默认值，要覆盖再展开

普通用户填不出"用了几米布"→ 按品类给**典型单件重量（克/件）**作默认值，用户可覆盖。
成分百分比之和必须凑齐 100%（±1% 容差），**不足不许静默补齐**，且要**三处同口径**执行
（2026-09-27 落地，见 `AGENTS.md` 1.3）：

- **配置层**：合计不齐 → 该条用料降级、**不给单价**（不齐时加权单价必然错，填 80% 等于按八折出价）
- **界面**：每条用料实时显示"成分合计 X%"，不齐时红底醒目
- **提交**：不齐时点「估算真实价值」**不跳转**，提示说清当前合计
- 容差只有一份真源 `config.PCT_TOLERANCE`，各处不许写死数字
- **「其他纤维 / 未标明」是必须给得出的出口**（国标允许 ≤5% 集中标注）：它计入合计但不参与定价，
  单价因此偏低、必须显式警示 —— 没有这个出口，用户为了凑 100% 只能瞎填一个纤维

**有价就必须在界面上看得见"多少钱、谁发布的、哪一期"**（2026-09-27 补）。
每条成分行下方显示「单价 + 发布机构 + 数据期」；取不到价的如实写"暂无权威报价"，**不许留空**
（留空在界面上等于整行消失，用户看到的是"这条成分凭空没了"，而不是"它没有价"）。
注意**"数据层齐全"与"用户能核对"是两件事**：纤维的出处曾经只写在数据选项的 `sub` 字段里，
而 picker 只渲染 `label` —— 那个字段从未被任何模板引用过，界面上根本查不到价格来源。

**计量口径：用户填「整件衣服有多重」，系统换算各部位（2026-09-27 改）**。

纤维原料价按**千克**发布，用量要落到**克**：`克 ÷ 1000 = 千克`，**零假设**。
但"这件衣服的面料单独用了多少克"是用户**答不上来**的 —— 那得把衣服拆开称。
所以界面上不再出现含义不明的「用量」：**只问整件衣服重量**（拿秤一放就有数，
是他唯一能自己验证的用量输入），各部位克数由 `config.distributeByTotalWeight()`
按该品类各部位**常见用料重量的合计**等比换算。

- **不填也算得出来**：回落本类常见值，**与加这一项之前行为完全一致**（不是按 0 计入）
- **口径差异必须写出来**：整件重量含拉链、纽扣、衬等辅料与五金，而重量表记的是**用料**重量，
  两者不严格相等 —— 不许造"各部位之和 = 整件重量"的假等式，
  要把基准克数与倍数显示在界面上（用户才知道那个克数从哪来）
- 用户手改过某个部位的克数就以他的为准，不再被整件重量覆盖
- 按「米」那条路仍保留（`每米重量 = 克重(g/㎡) ÷ 1000 × 幅宽(m)`），但已降为非主路径。
  没有换算桥就会 `单价(元/千克) × 用量(米)` —— **静默裸乘出无意义的数**

详见 `AGENTS.md` 1.3 与 5.5。

### 3.0.4 品牌不能一概而论，要逐品牌逐系列查

- **禁止**把品牌归到"无品牌/普通/知名/奢侈"四档就算完事 —— 四档只作查不到时的兜底
- 品牌记录的粒度是**品牌 × 系列**（优衣库基础款 ≠ U 系列；波司登主牌 ≠ 登峰）
- **实证**：波司登 2025/26 财年主品牌毛利率 69.1%、雪中飞 40.9%，同集团内差 28.2 个百分点；
  按档位一刀切会把这条信息彻底抹掉
- **同品牌的溢价还随渠道（官方旗舰店/奥莱/直播间）与品类（羽绒服 vs 针织衫）变化**
- 授权/贴牌品牌要特别标注：品牌与品质脱钩，吊牌价高但面料可能很次 ——
  对"看穿价格"是**反向陷阱**，不标会误导用户
- **口径不明的品牌一律不录**：LVMH、Kering 公开报道只给到经营利润率（Kering 2025 年 11.1%、
  LVMH 时尚皮具部门约 22%），与毛利率不是一个口径，混用会系统性低估

### 3.0.5 识别的每一类输出都必须走进估价（2026-09-27 补）

`recognizeByText()` 有三类输出：**品类 / 纤维线索 / 品牌档位**。
**少消费一类，就多一条静默偏差** —— 不报错、不降级，数字看着还挺正常。

- **品牌档位**决定设计费率：奢侈档 60% vs 普通档 12%，**差 5 倍**。它曾经被界面整个丢掉，
  于是"古驰大衣"会按普通品牌算出来
- **品牌库内能对上的**（爱马仕等 20 家具名公司）→ 预选品牌，用年报毛利率；
  **对不上的**（香奈儿 / LV / Gucci 等）→ 用档位兜底估算。
  两种情况界面都**必须说明**这是推测 / 档位估算，不是该品牌的年报数据
- 用户不知道"品牌档位"是什么 → **不做成输入项**，由识别结果兜底并在界面写明
- **换品类要一起动三样**：各部位克数、材料 / 品牌列表、两处选中的下标。
  手动切品类与"识别出品类"是同一个状态变化，**必须共用一份实现**（`planCategoryChange`），
  各写一遍必然漂移（识别那条曾忘了刷，克数停在上一个品类）

对应的界面口径与断言见 `AGENTS.md` 7.2、`verify-miniprogram.js` 第 12 组。

### 3.0.6 材料与品牌按品类分列，只排序不过滤（2026-09-27 补）

「有些牌子只做衣服，有些只做别的，不能一概而论」—— 这是事实，不是偏好。
波司登的毛利率来自**羽绒服业务**，把它摆在要给 T 恤估价的人面前，他要么以为我们在乱推荐，
要么挑中了、拿一个羽绒服口径的倍率去估 T 恤。材料同理：「全棉府绸（衬衣料）」
放在要做羽绒服的人的下拉里，只会让他多犹豫一次。

- **数据层各建一张表**：`FABRIC_CATEGORY`（18 条面料）/ `BRAND_CATEGORY`（20 家品牌）。
  **每家品牌还要有一句 `focus` 写清业务构成** —— 例如爱马仕的皮具箱包不在本模型范围内
  （只估衣物），不写用户会以为这个倍率能套到包上
- **判据只此一份**：一律走 `config.groupByCategory(items, categoryKey)`，
  界面不许自己写一遍 `filter`
- **只排序分组，不过滤**：品牌跨品类卖货是常态（波司登也出过 T 恤），
  硬过滤会让用户找不到自己那件衣服对应的选项，还以为是我们的库太差 ——
  那比"列表长一点"糟得多。默认只列"适合本类"，另给"显示全部"的入口
- **切换品类时选中项按 key 搬，不许沿用下标**：列表一重排，同一个下标指向的就不是同一家了。
  搬不到 → 展开全部再找；再找不到才回落，且必须说出来
  （沿用旧下标 = 用户选的波司登悄悄变成安踏，而且是静默的）

对应的界面口径与断言见 `AGENTS.md` 1.5、`verify-miniprogram.js` 第 13 组。

同为棉，长绒棉 137 级 26.72 元/kg vs 细绒棉 2227B 15.84 元/kg（差 69%）；
同为羽绒，90% 白鹅绒 984.45 元/kg vs 70% 灰鸭绒 369.01 元/kg（差 167%）。

### 3.1.1 「去品牌官网查」查得到的是成分，不是价格（重要）

| 要的东西 | 官网能否查到 | 真正的来源 |
|---|---|---|
| 各部位纤维**成分与含量** | **能，强制公开** | 水洗标 / 品牌官网与官方旗舰店商品页 |
| 面料/辅料**采购单价** | **不能**，品牌不公布采购价 | 绍兴e价通 / 柯桥纺织指数 |
| 品牌**加价倍率** | **不能**，品牌不公布自己的溢价率 | 上市公司年报/半年报毛利率反推 |
| 吊牌价（零售标价） | 能 | 官网 / 官方旗舰店明码标价 |

即：模型 = **成分（官网/水洗标）× 单价（轻纺城/指数）**。
**不许因为官网查不到价格就退回凭常识填价。**
品牌溢价换算：`加价倍率 = 1 / (1 − 毛利率)`，是**派生值，禁止手填**。
已核实例（2025H1）：海澜之家 45.99%、森马 47.81%、报喜鸟 64.89%、歌力思 70.91%、比音勒芬 75.88%；
行业整体 34.8%（纺织制造 18.7% / 服装家纺 50.5%），女装 67.7% 领跑。
**口径警告**：毛利率分母是品牌方「营业成本」，与模型「材料 + 加工」大体对应但**不等价**，属近似换算，界面须说明。

### 3.1.2 纤维成分标识的三个坑

1. **强制的是耐久性标签（水洗标），吊牌只是推荐性** → 引导用户拍**水洗标**，不是吊牌
2. 标称含量有**法定允差**（≤10% 允差 3 个百分点；≤5% 可归"其他纤维"）→ 界面不得宣称成分"精确"
3. 纤维名必须用**规范名称**（GB/T 11951 / GB/T 4146.1 / GB/T 17685）；
   "云朵棉""冰感丝""恒温羊绒"是**营销词不是成分**，识别到一律拒绝

**要求**：进入模型的价格必须可追溯到上述来源；无权威出处的必须标记为估算并在界面如实提示。

## 4. 核心功能（MVP 范围）

1. **拍照识别**：分两条路，能力不同、可分别落地
   - **端上 OCR（已实装，不需要后端）**：拍**水洗标** → 微信 VisionKit 读字 → 解析纤维成分。
     成分含量是国标强制标注的确定信息，比识别款式/面料外观可靠得多，**故作为主入口**（见 `AGENTS.md` 7.1）
   - **多模态大模型（第二阶段，需服务端中转）**：识别物品类别、材质、品牌等款式级信息
2. **手动上传/录入**：上传图片或文字描述物品信息，作为拍照的补充入口
3. **价值估算**：基于五段模型计算真实价值区间
4. **价格对比**：用户输入实际售价，App 给出对比结论（如：低于估值 / 合理 / 明显偏高）
5. **历史记录**：保存用户的查询记录，方便回看

## 5. 非 MVP（后续迭代，当前不做）

- 估价准确率反馈与学习机制

  小程序代码在 `/miniprogram/`（微信开发者工具直接打开该目录预览）；
  App 端为 React Native + Expo（SDK 57），原地保留、暂不维护
- **识别**：多模态大模型（拍照 → 识别物品类别/材质/品牌）
- **端上 OCR**：水洗标成分文字走**微信 VisionKit**（`wx.createVKSession` 静态图片模式，
  基础库 **2.27.0+**），**在端上跑、不出网、不需要服务端** —— 与上面的多模态大模型识别是两条路
  （见 `AGENTS.md` 7.1）。这也是本项目当前唯一能在「无后端」阶段真正跑通的识别能力
- **数据来源**：政府价格监测网站与纺织指数（见 3.1）
- **计算**：规则引擎 + 品类系数表，输出价值区间

已定：

- 先做微信小程序，验证产品后再决定是否平行推进 App
- 小程序的 `config/` `core/` `services/` 由项目根**单向同步**生成，两端共用同一份计算逻辑
- **小程序服务类目：工具 → 报价/比价**（官方定义即"商品价格展示、价格对比服务"，个人主体可注册、无资质要求）
- 大模型调用必须走服务端中转，Key 不进前端包。
  **小程序对此没有退路**：`wx.request` 只能请求已备案并加入后台白名单的 HTTPS 域名
- MVP 品类：**只做衣物**（2026-09-27 收窄）。鞋与包不做 —— 成本大头是鞋底 / 模具 / 五金 /
  版型开发，不是面料，按「面料价 × 用量」能算出一个看着像样但偏得很远的数；
  识别到鞋包时界面如实告知"暂不支持"并说明理由，**不许静默无反应**

**运行时不联网**（2026-09-27 核实）：小程序业务代码里没有任何 `wx.request` / `wx.cloud`，
数据全部打包在 `config/`（几十 KB）、计算在 `core/`、拍照读字走微信 VisionKit **端上 OCR**、
偏好存本机缓存。所以 **不需要服务器、域名、ICP 备案**，上线门槛只有"注册账号 + 提交审核"。
唯一需要网络的是**首次下载小程序包与版本更新**（微信平台行为，所有小程序都一样）。
**分界线**：一旦接大模型识别或做价格自动更新，就必须有能发 HTTP 的服务端 →
域名 + 备案，或走**微信云开发**（唯一免备案路径）。代价是价格只能是发版那天的快照。详见 `AGENTS.md` 7.6。

【待定】数据抓取的实现位置（服务端定时抓取建库 or 实时抓取）——无论哪种都必须在服务端
【待定】加工费（元/件）的权威来源 —— 目前为行业估算，需接代工厂报价数据

## 8. 合规与风险

- **数据抓取合规**：抓取政府价格网站与公开指数需遵守 robots 协议与相关法规，控制频率，仅采集公开数据
- **免责声明**：估值为参考结果，不构成购买建议或定价依据；结果页必须展示免责说明
- **识别准确率**：AI 识别可能出错，必须给用户修正入口，避免错误输入直接产出误导性结论
- **数据可信度**：必须向用户如实展示每个价格的数据等级（官方 / 指数 / 估算），不得让估算值看起来像官方数据
